插件如何找到 DSH 的能力？

以「给侧栏加一个任务入口」为例。DSH 预留侧栏的位置，插件把自己的组件登记进去，DSH 渲染侧栏时把它画出来。给模型增加能力也是类似的分工：插件登记模型适配器，DSH 在用户选用相应模型时把推理请求交给它。

实现这件事的起点是 ctx。它是 DSH 传给插件的上下文。客户端拿到的是面板、输入框等界面服务，宿主端拿到的是模型、工具和会话等运行服务。一个插件包可以同时提供两端的实现。

从安装到卸载

  1. 找到入口。包里的 dsh.bundle.patch 指向宿主装配清单，清单列出要加载的模块。dsh.client 声明客户端扩展及其依赖。
  2. 等依赖就绪。宿主模块用 export const inject = […] 声明所需服务。需要的服务准备好后，DSH 通过 Cordis 调用 apply(ctx, config)；带有 Config 声明的模块还可定义配置格式和默认值。
  3. 登记服务和回调。模块可以通过 ctx.provide() 提供服务，其他模块通过 ctx.get() 获取，或用 ctx.inject([...], callback) 等服务可用时再接入。运行中的事件用 ctx.on() 订阅。
  4. 释放资源。插件把取消订阅、关闭连接等操作交给 ctx.effect() 的清理函数，或由入口返回清理函数。插件卸载时，DSH 沿生命周期撤下这些扩展。

典型接口：插件可以向 DSH 要什么？

给界面增加入口

DSH 接口它解决什么问题
ctx.slots.inject() / ctx.slots.register()选择 DSH 预留的位置并登记组件。Loop 把入口放进侧栏，把授权交互放到会话界面。
ctx.inputTriggers.registerSource(source)给输入框登记候选来源。用户输入 / 时，DSH 可以展示插件提供的知识库或 Skill 选项。
ctx.layout.selectPanel(id)切换当前面板。例如用户点开任务时，插件请 DSH 显示对应面板。
ctx.typert.register() / ctx.remote.$mount()宿主端登记可远程调用的方法描述，客户端挂载同一份声明。界面随后能通过 DSH 找到宿主端处理函数。

让 Agent 使用更多能力

DSH 接口它解决什么问题
ctx.skills.register(skill)把随插件安装的操作指南登记为 DSH Skill。Agent 可以按需加载说明，了解怎样使用插件。
ctx.llm.registerAdapter(routes, adapter)把一组模型路由和处理推理请求的适配器交给 DSH。本例用它把已授权的 Loop 模型接入原生模型选择流程。
ctx.get("credentials")取得 DSH 的凭据服务。插件宿主端可通过提供方读取连接凭据，模型和界面通过相应功能使用连接。

读取工作区和会话

DSH 接口它解决什么问题
ctx.workspaceRegistry.list()列出 DSH 已登记的工作区及其会话。插件据此判断一条新消息来自哪个工作区。
ctx.sessions.get(id) / session.snapshotEvents(from, through)找到活跃会话，并按序号读取一段事件。适合已获准的历史回补，区间包含起点、不含终点。
ctx.sessionQuery.observeSession(id, options)以只读方式观察已保存的会话。插件可读取暂未打开的会话历史，用完后释放观察对象。

注册工具、投递消息与保存会话状态

DSH 接口本项目怎么用
ctx.tools.register(definition, {when})向模型登记一个可以直接选择的工具，例如协作目录或任务跟进。when 根据当前会话决定工具何时可用。前文的 tools/execute 则让插件参与一次已经发起的工具调用。
ctx.systemPrompt.context()按当前 Agent 和会话提供上下文说明。例如会话中有正在跟进的任务时，告诉模型怎样等待后续反馈。
ctx.agents.get(id)、sessionController.resolveAgent(id)、agent.send()找到或恢复对应会话的 Agent，再把允许投递的外部消息送进它的下一步或下一轮。适用于后台收到任务反馈后让 Agent 继续工作。
ctx.sessionProjections.register() / stateOf()告诉 DSH 怎样从会话事件整理出可查询的状态。插件据此读取投递回执，判断同一条反馈是否已处理。

客户端交互与宿主连接

DSH 接口本项目怎么用
ctx.uiSession.registerPendingInteraction()、ctx.uiConversation.userText.register()在会话中呈现待用户处理的授权请求，并为用户消息中的资源引用登记显示规则。
ctx.locale.register() / subscribe()、ctx.contextMenus.notify()登记界面翻译、跟随当前语言变化，并通过宿主显示操作反馈。
ctx.remote.session.modelCatalog() / selectModel()客户端通过 DSH 已有的会话服务读取模型目录，并为指定会话选择模型。
ctx.webServer.getOrigin()、ctx.connection.authenticatedUrl()启用 Worksite 时，宿主扩展向 DSH 取得本地 Web 服务地址和已认证的连接地址，用于接入远程工作站。

回调机制：DSH 什么时候来找插件？

插件先用 ctx.on(事件名, 处理函数) 登记。不同事件留给处理函数的决定权不同：有些只是告诉插件「发生了什么」，有些允许它参与决定「下一步怎么做」。

DSH 回调及入参（简写）触发时机与插件的作用
session/created → (session)会话建立。 DSH 公布新会话，插件可以识别它所属的工作区，为后续处理做准备。
session/event → (session, event)事后通知。 一条事件已经追加到会话日志。插件接到原始事件，可安排后台同步；这条消息本身已经记入 DSH。
session/flush → (session)等待检查点。 DSH 并行调用相关监听器，并等待它们返回。Loop 的监听器在这里提示本地写入器刷新；这个返回值不代表远端已收到。
session/disposed → (session)会话退出活跃状态。 插件可以释放该会话占用的资源，例如关闭相应的模型连接。
agent/pre-step → (payload, next)参与下一步决策。 每个 Agent 步骤开始前，Loop 先等待 next() 返回现有决定。如果决定继续，就把用户本轮选定的 Skill 说明补进即将交给模型的消息，再返回更新后的决定。
tools/execute → (exec, next)接手或放行。 DSH 准备执行工具时送来工具名、参数和会话。普通命令由插件调用 next() 交给后续处理；识别到 Loop Proxy 虚拟命令时，插件自己处理并返回工具结果。
ctx.remote.$on('llm/models-updated', fn)跨端通知。 客户端可以监听宿主模型目录变化。收到通知后刷新界面，用户就能看到更新后的模型选项。

怎样理解 next()？ 它把处理交给这条调用链的下一环。插件可以直接放行，也可以等下一环返回后再补充结果。会话消息通知没有这个参数；消息已经写入，观察者各自处理即可。

其他 Agent 回复后，消息怎样回到原来的 DSH 对话？

比如你在 DSH 里说「让测试 Agent 复核清单，有结果告诉我」。任务派出后，这次对话可以先停下来。过一会儿，测试 Agent 在 Loop 任务里回复「复核完成，第 3 项需要修改」。这条回复可以成为原 DSH Agent 的下一条输入，即使协作面板没有打开。

谁负责什么？ Loop 负责把符合订阅条件的消息送到本机；插件负责认出这条消息属于哪次协作；DSH 提供找到、恢复和唤起 Agent 的接口。模型可以据此向用户汇报，或继续原任务。收到远端回复本身不会扩大原任务授权。

collaboration_wait 是插件提供给模型的等待工具。它检查指定任务或话题的现有推送是否已就绪；返回 waiting_for_push 后，当前轮就可以结束。后续靠收件和 agent.send() 唤起，无需模型定时查进度。

任务默认推送话题订阅接收、确认与重连定位、投递与唤起

另一路事件流：把更新送到已订阅的界面

假设你在 DSH 打开一个会话的协作面板，希望看到同事稍后发来的进展。面板可以打开一条 DSH Remote 流式调用。这次调用一直保持，宿主端每产生一条相关更新，就沿同一条流返回一条，界面无需反复查询。

本项目声明了三条 DSH Remote 事件流

插件定义的流名称订阅者和收到的内容
collaborationEvents协作界面按会话订阅。打开时收到当前状态，随后收到任务、讨论等协作更新。
skillCatalogEvents客户端为当前工作区和会话订阅目录变化，供 Skill、知识等候选列表更新。客户端可在同一工作区共享底层订阅。
humanTaskEvents会话中的授权交互按会话 ID 订阅。先收到当前待办或空闲状态，随后随状态变化更新当前授权提示。

同一条任务反馈，可以有两个接收者

更新界面走上面的 Remote 流，前提是界面打开了对应订阅。让 Agent 继续工作走 DSH 的 agent.send(message, target, true)。宿主核对协作绑定、投递授权和回执后，可以把反馈送入正在运行的 Agent 的下一步，或送入空闲 Agent 的下一轮。后台接收 Loop 事件和唤起 Agent，都有自己的条件，关闭面板只结束对应的界面订阅。

前文的 ctx.remote.$on('llm/models-updated', fn) 是另一种订阅：DSH 已经定义了「模型目录变化」这个事件，插件监听它即可。上表三条流则由插件定义，DSH 提供注册、调用、传输和取消机制。

三条流的声明宿主注册与处理入口客户端挂载协作面板订阅与取消宿主推送与 Agent 投递

把接口串起来：两个典型过程

用户选中「周报 Skill」，然后发送消息

  1. 插件先登记候选来源。客户端调用 inputTriggers.registerSource()，告诉 DSH 输入框去哪里取 Skill 候选。
  2. 用户通过 / 选择团队周报 Skill。输入框记录用户这一次选了哪一项，并随提交的消息带入会话。
  3. DSH 准备让模型工作。它触发 agent/pre-step。插件识别这次选择，核对指定 Skill，读到对应内容后补进本步消息。
  4. DSH 继续模型调用。模型拿到用户要求和周报写法，生成草稿。这里输入框负责表达选择，步骤回调负责让选择真正进入模型上下文。

模型想查一项任务，为什么能得到工具结果？

  1. 模型发出工具调用。它通过 DSH 的命令工具提交 loop-proxy call task.get …。DSH 把当前会话和工具参数交给 tools/execute 回调。
  2. 插件接手这一次调用。Loop Proxy 识别命令，按真实会话定位连接，向 Loop 查询任务，然后按 DSH 工具结果格式返回。普通命令会沿 next() 继续；这条虚拟命令在进入系统 Shell 之前就已处理。
  3. 结果回到原会话。DSH 把工具结果交回 Agent，模型据此回答用户。另一个模块若订阅了 session/event，还可以独立观察此次工具活动，按同步设置处理记录。

同一次任务查询展示了两种扩展方式：工具回调可以提供执行结果，会话回调可以观察发生过的事。两者接在 DSH 的不同环节，能够各自发挥作用。
