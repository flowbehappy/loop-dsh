# Loop 插件开发与运行说明

本文中的命令均从仓库根目录运行，注明在 Loop 源码目录运行的命令除外。

## 开发与验证

需要 Node `^22.19.0` 或 `>=24.0.0`，宿主版本范围见插件 `package.json`。无需 Go 或 Loop checkout 即可构建和运行本仓测试。

```sh
npm run bootstrap
npm run check
npm test
npm run build:client
node plugins/loop-proxy-dsh/build-native.mjs /absolute/new/package
git diff --check
```

`bootstrap` 使用锁定依赖，AgentLoop 和 Skill 回归使用官方 DSH npm 包。UI 源码修改后需重建 `client.js`。设置 `LOOP_SOURCE_ROOT` 可额外对比 Loop 的派工 schema，不会自动启动服务或读取账号。

真实服务联调使用显式提供的隔离 Test Hub、全新 DSH Home 和合成账号，见[测试指南](testing/super-agent-e2e.md)。Node、SDK 或模拟上游测试不能替代真实 Web/Desktop 界面验收。

### Human 委托

直接描述要办的事即可。助手先使用自己的权限，缺少权限时会在原聊天中请求你授权可代办的操作。助手准备具体范围，点击“前往 Loop 确认”后在浏览器核对动作、资源、到期时间和可重复使用性。确认或拒绝后原任务会自动收到结果。业务管理动作需明确授权，应用委托限具体应用及动作。已有授权可在 Loop 账号设置中查看和撤销。

在 Loop 源码目录运行以下跨仓验证（相应插件目录需先完成 `npm run bootstrap`）。测试使用隔离 TiDB、合成浏览器身份及 Project 处理端，不启动正式宿主也不写入线上环境：

```sh
LOOP_NATIVE_PARITY_PLUGIN=/absolute/path/to/loop-dsh \
  go test ./internal/api/humandelegation -run '^TestNativeHumanParityIntegration$' -count=1 -v
```

受跟踪的派工工具使用单项 `tasks: [{title, description, assignee}]`；Host 自动补充绑定频道与已接受意图，并在写入前验证单项限制和目录身份。旧持久请求恢复仍使用原 wire 与 hash。

协作账本升级为版本 2 时自动保留原文件的 `.v1.bak` 私有备份。不要用旧 helper 覆盖新账本，也不要直接恢复备份覆盖升级后收到的回执；回退前保留旧发布包及其状态，避免旧版本读取新账本。备份在升级验收及恢复完成后再清理。

协作失败按影响范围处理：单条投递的冲突、撤销或待恢复状态保留在该投递上，不禁用智能体目录或清除其他已接受任务；账号授权与会话绑定由当前连接单独校验。目录更新只使缓存失效，不进入任务收件箱。目录通过当前连接实时查询，派工时再检查当前会话的协作频道。

提交仅包含源码、必要文档与测试，不包含凭据、运行数据、依赖目录或安装产物；不添加 `Co-Authored-By` trailer。

DSH 原生欢迎页保持原样。用户处理完欢迎页后，插件自动打开一次“更多 → 登录”的账号弹窗；关闭后不重复弹出，已有 Loop 登录状态时跳过。插件不再提供独立的 Super Agent 欢迎页。

左下角“更多”通过 DSH 公共插件插槽保留“设置、意见反馈、登录”三项；登录先打开账号弹窗，确认服务器地址后才进入 Loop 认证；地址由 Host 验证并记住。弹窗显示登录状态并提供退出登录；设置中的 Loop 项提供“上传未登录期间的聊天”，默认关闭。关闭时只上传登录期间收到的新消息，不在登录、重启或重新启用插件时回扫历史；开启时才通过已有授权补传可访问的历史。展开菜单不触发账号、模型或同步请求，也不修改 DSH 源码。Loop 登录后的单次确认会自动配置 Agent、模型授权和已安装的同步能力；已有可用模型选择保留，包括本地模型。重新登录导致 Loop 连接变化时恢复原来的同一模型；没有可用选择时优先选择第一个 Loop 模型，Loop 没有模型时选择第一个本地可用模型。需要服务端支持 `/api/v1/auth/external-host/connection`，普通 Loop 登录和 Agent/Human 授权保持原有流程。模型访问只复用 `loop.host + models.use`；插件不提供模型专用授权入口。

插件栏仅保留“任务”作为 Loop 常驻入口；“收件箱、通讯录、项目、工作流、知识库、云盘、数据空间、专家 · 技能、连接器”统一放在插件栏的“更多”中，每个模块只有一个入口，不再显示重复的“打开 Loop 项目”快捷项。

Loop 内嵌页面就绪后，普通点击 DSH 中指向当前 Loop 服务的资源链接，会打开对应 Loop 面板并定位到完整资源路径（保留查询参数和锚点）。该能力复用所有模块的导航映射，适用于聊天、引用及其他原生链接，不依赖某条消息或具体资源 ID。不同服务、未知页面、下载、修改键点击及页面尚未就绪时，继续使用 DSH 原有打开方式；插件停用后移除点击处理。资源权限仍由 Loop 页面检查。

“任务”默认打开与我相关的任务，“工作流”默认打开计划页。“专家 · 技能”使用 Loop 的 `/exports/roles` 入口，专家与技能详情页保持在同一插件面板内。

所有 Loop 面板共用的 iframe 统一配置复制与菜单粘贴、全屏、媒体播放、画中画和系统分享权限，仅向当前 Loop 页面来源开放，不随页面跳转扩展到其他来源。现有下载、表单和弹窗沙箱设置保持不变。权限声明不代替浏览器授权；安全上下文、用户操作和上层权限策略限制仍然有效。用途和不能通过 iframe 权限解决的边界见插件说明中的“Embedded page capabilities”。

DSH 统一登录使用 `loop.host`，设置配置服务端现有 OAuth 动作白名单，资源访问仍由普通 Agent 授权决定，默认开启读取、写入、模型和上传，删除与管理默认关闭。Human 委托具有独立的动作和资源范围；刷新令牌不扩大这些权限。未发布的旧三-token Host 连接升级后需要重新登录一次。

项目创建使用服务端 `project.create` 动作，在 Loop 账号设置“个人助手 → 操作权限 → 项目”中单独控制“创建”，新助手默认开启，读取/写入/管理均不隐含创建。操作始终以助手身份执行，创建者为助手，Human 为负责人并获得显式管理授权；可选关联频道会加入创建助手。公开频道可用 `channel.agent-add` 显式加入自己，项目可用 `project.join` 按现有加入/审批规则申请，知识库可用 `kb.bind` 的 `{kbId, selected}` 绑定或取消自己的选择。已有连接新增动作需保存相应权限设置后生效。Skill 可用 `skill.bind` 的 `{skillId, selected}` 绑定或取消自己的技能库，创建、修改和导入均记录助手身份。访问失败不切换主人身份；创建结果未知时先核对助手的项目列表，不自动重试。

本地工作区的新上传频道使用“工作区标题 (DSH 稳定短码)”作为显示名称；短码来自安装 ID 和本地工作区 ID，超长标题按 UTF-8 字节边界截短。同名工作区仍是不同资源。Host 服务端只按持久 ID 映射复用频道，首次创建遇到占用名称时选择数字后缀，不认领同名团队或频道；这需要配套的 Host 工作区绑定修复。已有映射、重试、重启和本地改名继续使用原频道 ID，不触发历史补传或修改本地标题。权限、网络和通用冲突错误不会被客户端当成重名重试。

账号只有一个登录状态，以 Host 的 OAuth 连接为准。每个用户在每个 Loop 工作区共用一个个人助手，首次登录创建“XXX的个人助手”，多台机器和重新登录复用身份。每台安装持有独立的一对 access/refresh token，业务、模型和同步共用它；退出一台不退出其他机器。Loop 设置的“个人助手”复用普通授权入口：模块开关配置 OAuth 动作白名单，资源列表使用现有 Agent 选择与授权。知识库默认补入用户可查看的库，手动取消后不会自动加回；访问时仍执行原来的 owner/sponsor 与资源检查。认证在外部浏览器完成；嵌入页没有独立登录入口。主凭据及模型/同步的非秘密引用保存完成后即可结束登录，目录刷新、默认模型选择、设备登记、页面加载和历史同步在后台执行。重启或页面 cookie 丢失时，Host 根据明确同意的页面恢复授权自动重建页面会话；退出时立即移除内嵌页并清除其缓存，完成同一连接的撤销。普通浏览器的 Loop 会话不受影响。

登录后，插件每 15 秒刷新已有授权的模型目录（上一次请求结束后计时）。用户新增的个人模型，以及管理员配置并授权给当前工作区的可执行模型，会自动出现在 DSH 输入框右下角的原生模型选择器中，无需重新登录或重启。删除或撤权的模型也会移出列表；刷新保留当前可用模型选择，空列表首次出现可用模型时按上述优先级补选。网络恢复后自动重试，模型凭据仍由受信 Host 保管。

Loop 模型调用的认证或权限失败保留服务端返回的说明，不统一改写为“API 密钥无效”。目录可见不等于当前调用可执行；应根据具体错误检查模型连接授权或上游服务。原生 DSH 模型保持原有错误显示。

Loop 服务重启可能使正在使用的模型会话失效，本轮会显示服务端错误。下一次发送时，Host 使用原有 OAuth 连接建立新模型会话。OAuth 授权已撤销时，重新建立会话会被拒绝并提示授权。

模型目录暂时刷新失败时，选择器保留当前连接最近一次确认的模型。后续刷新会同步模型增删和授权变化，每次实际调用继续校验模型会话。

Super Agent 在 Loop 账号设置的“个人助手”区域管理权限和设备连接；联系人不提供其普通私聊入口。它不接受其他人的 @ 或派工，宿主不会启动或恢复入站 Worker 会话。

聊天中的 `@` 可选择当前用户名下的 Loop 智能体和同一工作区的同事；每次打开和按名搜索都读取当前授权的通讯录。仅提及同事时只注入身份上下文，不发通知、不建任务。用户明确要求创建任务时，任务使用当前绑定频道的权限，负责人必须具有相应访问权；指定项目需先绑定其频道，不借 Human 身份创建个人任务。选择目标不打开协作弹窗，执行失败由 DSH 根据工具返回的具体原因回复。默认只分享任务描述，扩大到项目或其他资源时仍确认分享范围。

普通 `@` 随消息提交前会复核通讯录和成员身份。明确派工时，collaboration_prepare 先分页核对当前频道中的智能体。未加入的智能体仍可提及，DSH 会得到缺席对象和频道信息，可询问是否邀请。名单读取失败时保留未知状态。邀请经用户授权后重新核对成员，派工提交时由 Loop 再检查任务可见性。主动扩大分享范围仍走原来的分享确认和 Host 登记流程，旧草稿也保留原有绑定校验。失败或中断只结束本条派工，普通聊天仍可继续；再次派工需重新选择目标。过期引用、未确认分享及迟到回调不会恢复旧操作，也不会自动重试结果未知的派工。

插件在 DSH 原生 Skill 目录注册一条 `loop-proxy-harness` 摘要，新工作目录也能发现。模型按需加载入口中的能力地图，再通过 `loop-proxy guide <主题>` 读取智能体、任务、消息、知识与远端技能、记忆与文件、工作流与应用的具体说明；这些说明随插件分发，不请求远端目录、不注入业务数据。普通聊天按需加载通讯录指引后可查询当前连接可见的智能体，无需先 `@`、创建任务或绑定项目；写操作保留原有授权要求。其他业务动作仍遵循现有项目绑定和权限检查。

动作 schema 按需加载：`actions` 仅发现动作，`schema <actionId>` 默认只返回调用定义；需要完整输出结构时使用 `schema <actionId> {"includeOutput":true}`。工作流 DSL 示例和数据 API 过滤示例分别位于按需读取的 `workflows`、`resources` 指引，不预载到会话。在线文档用版本校验和 UTF-8 分段读取，工具结果标明实际读取范围；首尾读取不代表全文阅读。

派活前先按任务主题说明检查精确频道的成员关系；目标智能体尚未加入时，按用户授权使用原有频道邀请接口，确认加入后再派发。频道邀请涉及频道内容的分享，不能由在线状态或一次 @ 引用自动授权。派发失败不切换接口重复建任务；缺少邀请权限或无法确认任务归属时，明确说明阻碍。

协作指引按使用意图组织：`agents` 发现身份并指向讨论或派工，`messages` 解释频道、话题与触达规则，`tasks` 说明受跟踪的交付，`recovery` 按需解释权限与错误恢复。入口和普通聊天不预加载这些正文。频道支持多个 Agent；普通频道消息通过明确 @ 触达，话题参与 Agent 接收后续话题消息，无需重复 @。普通消息不建立 DSH 派工回执订阅。邀请需要频道管理权限和原有资源授权，默认权限不变。

个人助手发起多方话题讨论时，先开帖，在本轮已接受的本地用户消息下对精确话题启用接收，确认订阅后再 @ 参与者提问。新话题作者首次启用接收时，Loop 同时登记话题参与。推送回复进入原 Session，按需拉取沿用同一订阅 ID。收到截断正文时用 `message.get` 按话题和消息 ID 分段读全。原 Session 在后续轮次仍可发现订阅工具，创建或恢复接收要求当前已接受的本地用户消息；反馈轮可暂停原话题，不能扩大接收范围。操作顺序与证据核对见[消息指引](../skills/loop-proxy-harness/references/messages.md)。

`loop-proxy context` 同时返回当前 Agent 身份和工作区，避免把个人助手当成另一个执行器。动作发现与 schema 查询保留服务端结构化错误；目录缺项不等于接口不存在。命令本地校验失败区分语法、会话和执行选项，并返回 `dispatched:false`；合法 JSON 中的引号、换行及路径原样保留。按需加载协作工具不授予写权限，也不受旧的未绑定状态遮蔽；执行仍检查当前用户消息、目标接受和服务端授权。

插件通过 DSH 公开 system-prompt 接口提供简短的个人助手（Super Agent）身份与工作职责：理解目标、调查证据、在授权范围内作常规选择、执行并核验结果。具体操作说明继续通过 Skill 按需加载。代表用户执行不等于切换为 Human 身份或继承其全部权限；不因角色说明扩大工具、资源授权或分享范围。

能力目录、schema 和普通业务读写使用当前 Host 连接，不为尚未绑定的本地工作区创建上传频道，也不依赖上传权限；已有连接或项目冲突仍阻止执行。目标资源来自用户或授权读取，动作白名单、资源访问与审批继续由服务端原有 owner 检查；关闭上传不影响已授权的任务、文档等操作。协作仍需精确会话绑定与参与者权限。指引要求按用户目标主动发现能力，区分失败的子系统；使用历史材料时标明其时间和范围，不将旧测试结果当作当前权限或产品行为，并按目标读者验证交付物。知识检索保留精确来源，不将无结果或部分拒绝误报为全局无资料；本地子任务优先继承当前模型，另选模型时先发现真实路由。

长任务沿用原派工回执和已接受意图，不因首次派工确认的 15 分钟期限而失去管理能力；重启仍从原账本恢复。跟进继续实时检查账号、绑定、任务权限、负责人和操作预算。任务 done、正式 review approved 和执行中断均不结束委托；审批/返工复用正式 review，只有 end-management 明确结束当前 Task 委托。新本地续办成功后按可信 Session 序列替代该 Task 来源，关闭后不回退旧授权。没有独立本地工作时用 collaboration_wait 停止 goal 空转，保留目标并由原 Session push 唤醒。话题持续管理同样不受首次确认期限限制，但每个原用户消息与目标最多自动回复八次；预算耗尽后可暂停原订阅，继续讨论需新的本地用户输入。暂停、撤权和换绑后的晚到反馈不能继续写入。

用户可以用自然语言指定协作者，或要求助手自行选择。助手查询目录后调用 `collaboration_prepare`，Host 将精确目标绑定到本轮实际用户消息，再复用既有意图登记和派工回执；手动 `@` 仍可用，但不是唯一入口。准备阶段不建任务、不发消息、不邀请成员，只允许任务描述范围；频道邀请仍检查原有管理权限与用户对频道内容分享的授权。一次准备可覆盖多个目标，每次派工仍只创建一个 Task。远端消息不能自行成为新的用户授权。同一轮中，若只读目录或绑定状态查询失败，或参与者仍缺少权限，可用原参与者集合重新检查；并行检查合并为一次。绑定或意图登记的写入结果未知时不重新发起。

首次使用需要会话归属的协作或上传能力时，缺少映射的本地工作区按既有 host-sync 授权建立其稳定频道映射，避免依赖后台上传恰好先完成。已有会话可继承该本地频道；准备派工时恢复它的精确协作路由。这个过程不切换已有项目、账号、服务器或频道，不启用未登录历史上传；真实权限失败保留原因，不以另建频道或扩大权限绕过。

同步及设备接口保留服务端的具体拒绝说明。HTTP 403 表示该操作不被允许，不触发令牌刷新或要求重新登录；HTTP 401 才走已有认证恢复路径。授权缺失、资源访问受限与登录失效分别报告，不清除其他仍有效的能力。

协作目录保留服务端提供的 `targetId`、`memberId` 和 Agent 的 `agentId`。邀请按已选 `targetId` 精确查询并使用同条记录的 `agentId`，派工仍使用 `targetId`；不按名称推断身份，不把成员 ID 当作 Agent ID。映射缺失时停止邀请并说明原因。

协作目录同时保留服务端可选的 `mention`，用于直接填入频道或话题消息；旧服务端未提供时，消息指南说明如何用已核实的 `agentId` 构造精确提及。模型目录使用 `canNotifyHumanAboutTask`、`notifyHumanAboutTask` 和 `notifyHumanWhenTaskDone` 描述具体通知能力；原始 HTTP 字段保持兼容。消息指南按身份、范围、幂等与结果核验组织，能力标志不代表通用可达性。虚拟命令参数错误提供具体原因和纠正提示，且不回显请求内容。

## 构建与安装

```sh
plugins/loop-proxy-dsh/build-managed.sh /absolute/new/package
dsh plugin --profile web add /absolute/new/package.tgz
```

Desktop 使用官方 DSH 安装的插件管理命令与 `desktop` profile。构建不依赖 Go、代码签名输入或固定的 DSH 二进制摘要。凭据与插件生命周期由官方 DSH 管理；平台支持以相应宿主和原生依赖的实际验收为准。

升级时保留原 DSH Home 和旧发布包；不要为升级删除已有账号、会话或待发队列。旧 Go 连接的凭据不会自动导入原生 provider，需要重新登录建立原生连接。已保存的频道映射、账本备份和原事件 ID 继续按兼容规则处理。详见[安装与回退](../plugins/loop-proxy-dsh/README.native.md)。

Loop 服务端独立启动。使用 Vite 联调时，插件服务地址与 Loop 的公开地址应指向同一浏览器入口，由 Vite 代理 API。

## 端到端验收

用真实模型做场景验收时，把建测试账号和审批的凭据留在测试控制进程。单独设置 `DSH_HOME` 只分开配置和会话记录，宿主提供的终端或文件工具仍可能读取工作目录之外的文件。只验 Loop 业务的轮次可以在 DSH 的工具执行层限定可用工具，并用无害命令核实限制生效。

Web 和 Desktop 由官方 DSH 管理插件生命周期。运行中通过 DSH 原生插件页关闭 Loop 后，DSH 继续运行，重新开启时恢复连接。关闭插件不等于退出账号，不删除原登录、项目绑定或会话上传偏好。已安装同步时，仅开启“上传未登录期间的聊天”才补传历史；默认从重新开启后登录期间的新消息继续，已入队事件仍复用原有持久队列与事件 ID。

切换插件可能触发 DSH 的组件重载；正在进行的 Loop 请求会取消，结果未知的写入不自动重试，旧会话绑定和临时审批不跨连接保留。原生验收需覆盖停用后重启、连续开关、普通模型会话、Loop 模型与历史同步恢复，不能仅用连接单测推断整个界面无感切换。

服务端测试实例由 Loop 仓库构建并启动；客户端与插件由本仓库构建。使用独立 DSH Home、工作目录、测试账号和数据库，记录双方版本、插件摘要与官方 DSH 版本。

基本流程包括：Loop 登录与单次连接确认、自动选择模型并获得真实回复、调用 Loop 业务能力并回读结果、安装同步时无需额外登录即可上传并在 Loop 回读、重启后恢复连接并继续会话。启用 worksite 时还需通过 Loop 入口打开对应安装，验证 HTTP/RPC/WSS。Desktop 必须单独操作实际原生界面；Node、SDK 或模拟上游测试不能替代这一步。

DSH 的 `loop.host` 在同源、同工作区内访问 Agent、模型和会话同步，各模块仍检查普通 grant 的动作白名单和领域授权。普通独立授权保持原有用途范围；worksite 和浏览器页面授权保持独立边界。验收报告分别列出实际执行、失败和未执行项，不把历史结果视为当前发布验证。

### Loop 知识库

输入 `/` 可搜索和选择当前 Loop 连接有权读取的知识库，与原生命令、本地 Skills 和 Loop Skills 并列。知识库和 Loop Skills 的搜索同时匹配显示名称中的 `Loop` 前缀，不区分大小写；输入 `/lo`、`/loo` 或完整 `/Loop` 均可发现候选。选中后输入问题，助手按需枚举库内文档与来源、检索内容并读取证据。仅选择本轮需要的库；选择不会新增授权，也不会加载整个库或其他库。

目录使用既有服务端推送，新增授权、删除或撤权后，下次打开时更新；已打开的候选与已选择引用保持稳定。读取失败会在聊天内说明原因，可重试连接、恢复原有访问权限或重新打开 `/` 选择可用知识库。需要支持 `kb.catalog` 和 `kb.retrieve.kbIds` 的 Loop 服务端，不修改 DSH 上游源码。

发送后的 Loop 知识库引用显示库名称；内部引用保持不变，用于标识用户所指的库，实际权限由 Loop 在调用时校验。

Loop 通用操作说明通过已有 Skill 和 `loop-proxy guide` 按需读取。`tasks` 或 `agents` 指引只为当前回合显示协作工具，不授予操作权限。普通消息不自动准备任务续接，也不重复注入历史联系人、任务列表或固定协作规则；模型从历史回执取得任务 ID，实际调用写操作时 Host 才绑定当前用户消息并执行原有校验。回合结束后收起工具，后续需要时重新读取指引。知识库选择只附带本次库 ID 和指引入口，业务调用沿用 Loop 服务端鉴权；已读取的 Skill 和结果仍属于正常聊天历史。

虚拟命令接受模型自动补齐的当前会话目录、前台模式和非提权沙箱默认值；这些参数不进入 shell 或扩大 Loop 权限。协作目录首屏可省略 cursor 或传空字符串，后续只使用返回的 nextCursor。context 中的 binding 标明这是保存的映射，资源访问仍需按具体操作检查。
